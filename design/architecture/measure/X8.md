# X8: arc granularity

**Status label:** measurement (pyslang only; no Lean). Agent M, WS4, 2026-11-02. Branch `arch-measure`, base `integ1102` at `d5fbdbc4`.

**Question (ARCH-NOTE §7 X8, §4.6, §5.5, §9).** On real cores, how many combinational cycles between modules appear when a
child's dependencies are summarized per PORT and disappear when they are summarized per BIT or per STRUCT FIELD? The stop
rule: if port-level arcs suffice everywhere measured, bit/field granularity becomes an option, not the default.

## Method (READ `arcs.py`; JUDGED soundness argument)

Per distinct module body, a node per bit of every variable, net and child port. Edges come from continuous assigns, net
initializers and combinational processes (`always_comb`, `always @*`, `always @(a or b)`, `always_latch`), executed
abstractly with blocking-read environments, control dependencies and joins. Edge processes and `initial` blocks give no
edges. A child enters its parent only through its arc summary, coarsened at four granularities: **module** (every
combinational output depends on every input that reaches some output), **port**, **field** (leaf struct field; arrays of
structs per element and field), and **bit**. The parent's own logic is always bit-precise, so the granularity changes only
the child arcs. Strongly connected components are grouped by shared signal. A **cycle** is a group with a multi-node
component, and it is **module-level** when it passes through a child port.

The abstraction only ever adds dependencies: whole conditions, dynamic selects over every candidate, `+`/`*` bit `i`
on bits `0..i`, conservative fallbacks (3, 8, 0, 0 and 55 sites at the five points; `LValueReference` and `Streaming`).
So **a count of zero is an upper bound that holds**. Two rules remove dependencies, and both are exact at a fixed
parameter point:
- parameter folding: `P & x` with `P = 0`, `?:` and `if` on a constant;
- `case` coverage, in the `2state` and `yosys` modes only.

The self-test fixture checks each granularity and mode against hand-computed answers: a bit-level false cycle, a
struct-field false cycle, a real two-instance loop, a port pair that is false only at module granularity, a parameter-dead
path, a latch, and a full-coverage `unique case`.

**Cycles that close through child arcs** (mode `lrm4`; modes change only hold groups):

| design point | module-level cycles at module / port / field / bit | module-granularity cycles that vanish at port | summary size (arc pairs) port / field / bit |
|---|---|---|---|
| `ibex_core@default` | 3 / **0** / 0 / 0 | 3 of 3 | 970 / 1204 / 57068 |
| `ibex_core@maxperf` | 3 / **0** / 0 / 0 | 3 of 3 | 1130 / 1349 / 61140 |
| `cv32e40p_core@default` | 3 / **0** / 0 / 0 | 3 of 3 | 899 / 899 / 31942 |

| `cva6@cv32a6_imac_sv32+WT` | 6 / **0** / 0 / 0 | 6 of 6 | 1149 / 5090 / 328627 |

There are no intra-module cycles at any granularity, at any point.

**What the module-granularity cycles are.** These are the cycles that a summary with no arcs at all would invent. Each is
broken by port arcs:
- `ibex_ex_block`: the ALU and the multiply/divide unit share the adder. `multdiv.alu_operand_*_o` depend on
  `imd_val_q_i`, `op_a_i` and `op_b_i` only, never on `alu_adder_ext_i` (confirmed in the source, `ibex_multdiv_fast.sv`
  385-511). This is ARCH-NOTE §4.8's "acyclic port by port".
- `ibex_id_stage`: the controller's flush.
- `ibex_core`: CSR access.
- cv32e40p: OBI request/response, aligner/prefetch valid/ready, controller stalls.
- cva6: scoreboard/issue `issue_ack`, MMU/load-unit DTLB, dcache control read/miss, AXI shim `rd_req`/`rd_gnt`, cache
  subsystem `data_req`/`data_ack`, commit stage. These are cva6's struct-bundled handshakes. At this parameter point port
  arcs already break them; without folding, two need field arcs (below).

**Without parameter folding** (`x8_nofold.json`, mode `nofold`). This is what a summary must carry if it is stated for
EVERY parameter value without conditions: `P & x` keeps `x` when `P = 0`, and an `if (P)` runs both arms.

| design point | module-level cycles at module / port / field / bit | intra-module cycles | summary size port / field / bit |
|---|---|---|---|
| ibex (both points) | 3 / 0 / 0 / 0 | 0 | 1067 / 1351 / 59853 (default) |
| cv32e40p (both points) | 3 / **2 / 2 / 2** | 1 | 1006 / 1006 / 37790 (default) |
| `cva6@cv32a6_imac_sv32+WT` | 7 / **2 / 0** / 0 | 1 | 1411 / 7124 / 574555 |

- cv32e40p: both cycles persist at bit granularity, so no granularity removes them. They run through the FIFO's
  `empty_o = (cnt == 0) & ~(FALL_THROUGH & push_i)` (`cv32e40p_fifo.sv:60`), which the prefetch buffer instantiates with
  `FALL_THROUGH = 0`. Only a parameter CONDITION on the arc `empty_o <- push_i` removes them.
- cva6: two struct-bundled handshakes are cyclic at port granularity and acyclic at field granularity: frontend ↔ icache
  (`icache_dreq_i/o`) and ex_stage ↔ cache subsystem (`dcache_req_ports_i/o`, arrays of request/response structs).
- The intra-module cycles (`cv32e40p_cs_registers.mstatus_fs_n`, cva6 `decoder`) also exist only on parameter-dead paths.

**Within one module, what a rank must range over.** This is the R-COMB question. The module graph is quotiented with the
child arcs exact:

| design point | bodies with a cycle when every bit a process writes is ONE node (a rank on processes, today's `Acyclic`) | with whole signals as nodes | with struct fields as nodes |
|---|---|---|---|
| `ibex_core@default` | 2 of 25: `ibex_controller`, `ibex_multdiv_fast` | 0 | 0 |
| `ibex_core@maxperf` | 2 of 27: same | 0 | 0 |
| `cv32e40p_core@default` | 3 of 24: `cv32e40p_if_stage`, `cv32e40p_controller`, `cv32e40p_id_stage` | 0 | 0 |
| `cv32e40p_core@pulp` | 3 of 25: same | 0 | 0 |

Example (source READ, `ibex_controller.sv`). The FSM `always_comb` (line 542) writes `halt_if` and reads `id_in_ready_o`
(line 628), and `assign id_in_ready_o = ~stall & ~halt_if & ~retain_id` (line 1023) reads `halt_if`. That is a cycle
between two processes. At signal level it is not one: inside the FSM, `id_in_ready_o` steers only `ctrl_fsm_ns`, a register
input.

**Holds** (a combinational process keeps a value on some path), by mode:

| design point | lrm4 | 2state | yosys | default-less `case` statements |
|---|---|---|---|---|
| ibex (both points) | 0 | 0 | 0 | 0 |
| `cv32e40p_core@default` | 16 | 1 | 1 | 32 |
| `cv32e40p_core@pulp` | 17 | 1 | 1 | 33 |
| `cva6@cv32a6_imac_sv32+WT` | 19 | 19 | 19 | 6 |

cv32e40p's 15 (16 at `pulp`) holds that vanish in `2state` are default-less `case` statements whose constant items cover
every 2-state selector value, for example `unique case (imm_a_mux_sel)` in `cv32e40p_id_stage.sv:610`. Under the LRM's
4-state reading an x/z selector matches nothing and the variable holds. The one that stays is the clock gate's latch. Of
cva6's 19, some are real (for example, `cva6_fifo_v3`'s `data_ft_n` is assigned only `if (FPGA_EN && FPGA_ALTERA)`), and
some may be over-approximation from loops that were not unrolled (8 fixpoint loops). Holds are a by-product here, not
audited.

## Verdict

1. **At a parameter point, port arcs suffice everywhere measured** (5 design points, 3 cores; 198 module bodies over the
   five points, ibex and cv32e40p bodies repeating between their two points): 0
   module-level cycles at port granularity, and all 18 cycles that an arc-less summary would invent disappear there.
   Field and bit arcs break nothing more and cost more (field +0 % to +343 % arc pairs, bit 35× to 286×). D6 as written
   ("per module at a parameter point") can therefore use port arcs.
2. **For arcs stated over every parameter value, port arcs do not suffice, and neither does any granularity alone.**
   - cva6's two cache handshakes need FIELD arcs. This bears out ARCH-NOTE's JUDGED "struct-bundled handshakes would
     need field-level ones", but only for parameter-uniform summaries.
   - cv32e40p's FIFO needs a parameter-CONDITIONED arc, and bit granularity does not help.
3. **Bit granularity was never needed.** Every cycle that bit arcs remove, field arcs or a parameter condition remove too.
   The recommended representation, by X8's stop rule: **port arcs carrying parameter conditions, refined to struct
   fields where a port is a struct** (cheap: +0 % to +343 % over port); bit arcs as an option only.
4. **A rank on processes does not exist for 2 of 25, 2 of 27, 3 of 24, 3 of 25 and 8 of 97 bodies (the five points), but a
   rank on signals does for all but one, and a rank on fields for all.**
   - This bears on R-COMB beyond E-core-0, that is, on G-B.
   - Today's `Acyclic` (a rank on process indices, the certificate that `lowerComb`, `sv_structure` and every svGolf record
     carry; X3) would refuse `ibex_controller`-shaped blocks.
   - ARCH-NOTE's R-COMB hypothesis "acyclic at bit or field granularity" holds for all 198 bodies.
   - The §4.3 termination sketch, "running a node can only trigger nodes of higher rank", is false when the node is a
     process: the FSM above is re-triggered by an assign of higher rank. With signal or field nodes the measure has to
     argue that a re-run caused by a change of input `x` changes only outputs that depend on `x` (JUDGED).

## What this changes in ARCH-NOTE

- §4.6 row "per-port arcs → arcs per bit or field", §5.5 "child summaries carry arcs at bit or field granularity", D6/D9:
  bit granularity is never needed on ibex, cv32e40p or cva6.
  - At a parameter point, port arcs suffice.
  - For a summary valid at every parameter value, struct ports need field arcs (cva6, 2 cycles), and some arcs need a
    parameter condition (cv32e40p, 2 cycles).
  - Recommend field-refined port arcs with parameter conditions as the default, bit as an option.
- §9 risk "compositionality fails on real hierarchies": no spurious cycle survives at bit granularity except the 2
  parameter-dead cv32e40p ones, which only conditions remove. That is the "add per-path arcs" branch in its parameter
  form, not "flatten".
- §4.3 R-COMB:
  - The hypothesis is right at field (and almost always signal) granularity, but the proof sketch's measure must not be
    per process.
  - G-B's "negative cyclic design" must not be a design that is cyclic only at process level.
  - X3's remark that "the lowered certificate is already process-level" is a limit as well as a convenience:
    process-level certificates cover the svGolf references, and 18 of the 198 real bodies have none.
- R-HIER / D9 at a symbolic parameter: arcs need parameter conditions (finding 2).

# X2: process atomicity versus preemption (§4.7), measured on E-core-0

**Status label:** measurement (a copy of E-core-0's executor run through the slot; the extractor and pinned Xcelium
traces as inputs). Agent M, WS4, 2026-11-03. Branch `arch-measure`, base `integ1102` at `d5fbdbc4`. The executor is
copied from agent A's `arch-x1` at `edce9ef8` (`Kernel/Core0.lean`, `Elab.ofDesign2` from `Kernel/Core0Obs.lean`); none
of A's files is edited or imported. ARCH-NOTE §7 X2 and the JUDGED prediction it tests: "preemption breaks nearly every
`always_comb` fed by another process". Data: [`x2.json`](x2.json).

## The instrument ([`X2Preempt.lean`](X2Preempt.lean), [`x2_rows.py`](x2_rows.py))

**The copy.** These are copied from E-core-0:
- typed values and writes (LRM 6.11);
- the flat view that `evalPure2` reads;
- an assign's activation;
- an `always_comb` body's statements:
  - blocking assignments to static windows, `if`, `case`/`case inside`, `begin … end`;
  - NBA, dynamic and concatenated targets are refused;
- the sensitivity: an `always_comb` is not sensitive to a read overlapping what it writes;
- triggering;
- the input events of a slot (`applyInputs`, `nextSlot`, `start`).

The store is an array indexed by declaration, so that configurations can be compared. E-core-0 is flat, so this loses nothing.

**Three policies, each explored exhaustively (breadth first) from the same slot start:**
- **`atomic`** is E-core-0's `step`. Any ready process may run next, and it runs as one activation. The processes
  whose sensitivity saw a change between the stores before and after the activation become ready.
- **`stmt`** adds preemption between statements (LRM 4.7). An `always_comb` activation is a sequence of units:
  - a blocking assignment (evaluate and write);
  - the evaluation of an `if` condition, or of a `case` subject and its patterns, which selects the branch run later.

  After every unit, the waiting processes whose sensitivity saw a change in that unit become ready. A started and
  suspended process is not waiting, so it is not woken (LRM 9.2.2.2: the block waits on its sensitivity only between
  activations). Starting a process and running its first unit are one move. Continuous assigns stay one unit (E-core-0's
  fused evaluation and update).
- **`eval`** also splits each blocking assignment into its evaluation and, possibly after other processes run, its
  write (LRM 4.7: "place the partially completed event as a pending event").

Every `stmt` schedule is an `eval` schedule (evaluation and write back to back). So a `stmt` change is an `eval`
change, and the reverse need not hold.

**The comparison.**
- Every slot starts from the canonical atomic run's store, using the lowest-ready-process Choice.
- A row is **invariant** under a policy when every slot's set of closed stores equals `atomic`'s. By induction over
  slots, every behaviour is then the same.
- A row **changes** when some slot closes with an observed sample (the case's sampled signals) that no atomic schedule
  produces. The witness is the shortest such schedule:
  - `a<q>`: an assign activation;
  - `c<q>`: a whole `always_comb` activation;
  - `s<q>`: start process `q` and run its first unit;
  - `r<q>`: resume `q` for one unit.
- **`internal`** means only unobserved variables differ.
- **`budget`** and **`time`** mean the exploration stopped before deciding: 4000 configurations per exploration, and
  30 s of wall clock per row (svGolf: 3000 configurations).
- **`no-statement`** means an assign-only design. Every policy then has exactly the atomic moves, so it is invariant
  by construction and not explored.

**A sound reduction** (the only one): a process that no other process reads or writes, and that reads nothing another
process writes, moves alone. It commutes with every move and is never woken by one: a singleton ample set.

**Runs.** Five slot acquisitions (a compile check, then four runs), each process at most 10 minutes of interpretation (`lake env lean --run`). Rows are merged
by name, a later run replacing an earlier one:
- the assign-only rows come from the first run;
- every `always_comb` row was run with the reduction;
- the time cap was added for the last 43 rows, after `wl_rowloop_n2` alone took 428 s.

The raw `X2ROW` lines stay in scratch; [`x2.json`](x2.json) holds the merged rows and the summaries.

**The canonical run is checked against Xcelium:** the per-cycle samples are compared with the pinned trace of
`harness/sv/xcelium_golden.json`.

How the two `stmt` changes happen (`acg_alias_far`: `assign w = a; always_comb begin y = w; z = b; end`). At time
zero every process is ready. The block starts and runs `y = w` while `w` is still x. The assign then runs and changes
`w`, but the block is running, not waiting, so it is not woken. The block finishes `z = b` and the slot closes with
`y = xx`. Under atomic execution the block is woken again, because it was waiting when `w` changed.

The three `stmt`-invariant fed rows read the fed variable in their LAST unit (`acg_alias_wr`), in a single-unit block
(`acg_alias_copy`'s `always_comb w = t`), or are re-woken by their own later write through the assign
(`acg_alias_assign`: `y = w; t = a;` with `w = t`). In each, the read can go stale only between an evaluation and its
write, which is exactly what `eval` adds. The ARCH-NOTE example `always_comb c = b & d;` is of this kind.

## D. Two findings about E-core-0 itself (MEASURED on the copy; for agent A)

1. **`acg_xproc_bits`: E-core-0's `always_comb` sensitivity disagrees with Xcelium** (MEASURED on the copy, whose
   `Elab.sens` is A's verbatim). The canonical run gives `y=00`, `11`, `11` at cycles 1, 3 and 5; the pinned Xcelium
   trace gives `y=01`, `10`, `1x`. The block writes `t[1]` and reads all of `t`. E-core-0 drops a read that overlaps a
   written window, so it is never woken by `t[0]` (written by the other block), which is Icarus's behaviour. Xcelium
   keeps the unwritten bits, as the LRM text says (9.2.2.2.1 b). This is the Xcelium row A's open question (X1-NOTE §8)
   asked for. The row declares only an Icarus disagreement (`iverilog-comb-bit-split-sensitivity`), because run2
   agrees with Xcelium there; E-core-0 at `edce9ef8` does not.
2. **`dyn32`** (no declaration in `cases2.json`): on indexed part-selects that overhang the vector, the copy returns
   the in-range bits (`minus2=11xx` at `s=0`) where Xcelium returns all-x. That is the class of the declared
   `xcelium-runtime-partial-part-select-all-x`. E-core-0 has no select guard, and its runtime refusal covers only the
   `ArraySel:partial-overhang` node (31 rows). Not investigated further.

## E. Verdict

1. **The JUDGED prediction holds at the LRM's own granularity, and holds for most fed blocks between statements**
   (MEASURED, B, C). Preemption inside a statement (`eval`: "at any time while evaluating a procedural statement")
   changes an observation in 10 of the 11 decided rows with an `always_comb` fed by another process: golden 6 of 7,
   svGolf references 4 of 4. Preemption only between statements (`stmt`) changes 5 of 8: golden 2 of 5, svGolf 3 of 3.
   The survivors read the fed variable only in their last unit, or are re-woken through their own later write (B).
2. **Every row with no fed `always_comb` is invariant** (MEASURED): 114 of 114 golden rows with `always_comb`, all 336
   assign-only rows, `sbox_table` and the 4 leaderboard records. That is the expected shape (JUDGED). Within a slot,
   such a block reads only inputs and its own writes, which do not change while it is suspended; every reader of its
   outputs is woken by each write. So "no `always_comb` reads a variable another process writes" is a sound per-design
   census for the stop rule's C-style alternative. It passes trivially on this corpus.
3. **The stop rule, read literally, fires: 450 of 460 golden rows are preemption-invariant.** But the invariant majority
   is an LRM conformance corpus whose `always_comb` rows read only inputs (114 of 124). On real RTL the census rarely
   passes: in `ibex_alu@rv32bnone` (X7's sliced variant, signal-level census of its envelope, READ) 8 of 11 `always_comb`
   blocks are fed by another process, and the only `always_comb` svGolf references are fed and change. JUDGED: the
   census is worth having beside the narrowing, not instead of it. It retires sv-div-4 per design where it passes, and
   on ordinary RTL it does not pass.
4. **sv-div-4's `gated` text is too narrow** (MEASURED). It says "the narrowing is observable only where a block reads a
   value another process derives from the block's own writes". In `acg_alias_far` and `acg_alias_bits_ok` the fed value
   comes from an input (`assign w = a`; `assign t[0] = b; assign w = t[0]`), and preemption between statements changes
   the observation at time zero. Proposed wording: "observable where a block reads a variable another process writes
   in the same slot".
5. **Input to sv-div-4's retirement condition.** "A per-design census that makes the narrowing exact" can be the fed
   census of item 2: sound on everything measured here, and decidable from the elaborated process list.
   Undecided: 8 fed rows hit the budget or the time cap (the `wl_rowloop` family, `add_proc` at N=16). A partial-order
   reduction beyond the independent-process one would be needed to decide them, and none of them is needed for the
   verdict.

**Not done.** Edge processes (E-core-1, X4) are outside the copy. Continuous assigns stay fused (E-core-0's ruling), so
an assign's evaluation/update split is not measured. The `mul` references were not run (assign-only).
